Patronus and native cloud browser evaluation

Reusable protocol and execution plan

11 October 2026

# Current result and purpose

The evaluation is ready to run after Patronus becomes reachable. No paired browser trials have been completed, and no browser is a measured winner. The read-only Patronus capabilities request returned MCP error -32603 at 20:30 UTC on 11 October 2026. This is a connector transport observation; it does not show that any target website failed.

The question is where Patronus materially improves completion of the same task, under which session conditions, and at what cost in time, tool calls, and user attention. The answer should be a case-specific routing map with uncertainty. A single overall access percentage would hide the jagged behavior that motivated the work.

The accompanying kit contains 15 cases, a 20-arm public pilot schedule, an empty observation log, result templates, an offline planner and validator, and an analyzer. It does not pretend to be an automatic browser driver. The operator follows the supported live browser tools and records evidence in the supplied schema. No Alpha repository, production service, plugin connection, or recurring schedule was changed.

# Comparison arms

The primary comparator is native interactive cloud Chrome, controlled through the dot cloud browser. Jensen’s offline desktop is outside this comparison. Web textual fetch is a separately named diagnostic baseline and fixture-discovery tool. It is never counted as native interactive Chrome.

Patronus browser reader uses read mode with browser rendering forced and one page per task. Auto rendering and HTTP rendering are separate optional strategies. Do not combine their outcomes with forced-browser reader results or assume what auto selected if the backend does not report it.

Patronus direct download is a separate arm for file tasks. Patronus headed desktop is the proposed interactive arm for buttons, players, and authenticated flows. Project context describes headed Chrome and handoff support, but this session has not verified a callable Patronus desktop interface. The exposed start API is retrieval-only. Mark desktop capability unavailable until a live supported interface is discovered. Do not invent a desktop API or claim a reader can perform arbitrary clicks.

Compare only modes that can attempt the same task. An unsupported interaction is a capability boundary, not a failed extraction experiment. Keep that boundary visible in the practical routing map while excluding it from paired site-access statistics.

# Cases and first pilot

The first pilot has five public cases and two repetitions per case, each with native and Patronus arms: static HTML facts, a structured W3C tutorial, rendered Onyx copy, an actual PDF download, and a public podcast transcript. The schedule counterbalances which arm runs first. Twenty arms at a 120-second limit permit up to 40 minutes of task execution; allow at most 60 minutes including preflight and evidence review. This is a diagnostic pilot, not enough evidence for a lasting routing rule.

The wider public suite adds delayed content after a button click, complete transcript file download, portfolio-embedded reel playback, direct Vimeo playback, a specified public X post, and retrieval continuity after a no-poll interval. Embedded and direct video targets are companion contexts. Transcript reading and downloading are different tasks on the same domain. Keep both distinctions, but do not double-count them as independent domains in a global access score.

The manifest preserves unresolved X10 and Loom targets without guessing their domains. It also includes gated DMV status and Apple order regression cases. The earlier disputed copy is on Onyx; that correction is preserved. No private order number, government identifier, login credential, or tracking-token value is included.

Every case defines the user task and required checks. The known fixture facts are seeds for a run-time reference. Dynamic pages require fresh adjudication. If the target changed, freeze a new reference before either arm; if it changes between arms, mark the pair incomparable. Never use a search snippet as proof that the requested post or page was accessed.

# Session and environment controls

Use the same canonical URL, account entitlement, requested facts or actions, language, consent policy, time limit, and allowed interactions on both arms. Record actual browser and tool versions, rendering mode, operating environment, viewport, locale, region when observable, profile alias, session age, and authentication state. Unknown values remain null. Network topology is a product difference to record, not something to claim is controlled.

Cold public means verified logged-out access with fresh isolated evaluation state. Warm public means the same isolated profile after exactly one unscored priming load. Warm authenticated means the same authorized account and privileges on both arms. Never clear the user’s real browsing profile or export cookies to manufacture parity. Create an isolated profile only through a supported and authorized mechanism.

If isolated profiles cannot be selected, use public observed state and label cache and authentication uncertainty. Existing access in one product can be a useful practical advantage, but it is not evidence of a better browser engine. A warm authenticated Patronus run and logged-out native run are an access-state comparison, not a matched performance pair.

A condition key identifies the frozen tool versions, profile category, task budget, ground-truth policy, and relevant environment settings. A result pair is eligible for routing analysis only when both arms have the same condition key and reference, confirmed equivalent prerequisites, and start within ten minutes of one another.

# Execution procedure

First, read each product’s supported capabilities without changing authentication or settings. Record the availability result separately. Then run a small public control through both products. If the connector cannot start work, stop the dependent comparison and leave website trials not run. If a browser starts but a website fails, retain the attempt with the narrowest evidenced failure stage.

Generate a seeded schedule. The supplied seed is 10112026. Case order is randomized within each repetition; AB and BA order alternate within each case and profile. Run paired arms sequentially with at least 15 seconds between requests to the same origin and no concurrent pairs against one origin. The operator must enforce the pacing; the offline planner does not make requests.

Before each arm, confirm the assigned state and save a start time. Use the case task verbatim. Count all navigation, polling, evidence, result, and artifact tool calls. Retrieval defaults are one page and a five-megabyte file ceiling. The normal task cap is 120 seconds; the interaction fixture is 90 seconds and video or persistence cases are 180 seconds. The cap includes job queueing, rendering, retries, and result or artifact retrieval.

Allow at most one safe navigation retry within the same budget. Retain the first-attempt outcome and the final outcome so a recovery does not erase a failure. Use returned job IDs and the same idempotency key when a start result is uncertain; do not create a duplicate job to see whether it worked. Follow the live service’s polling guidance; absent guidance, increase waits up to 15 seconds rather than poll continuously.

Stop on a denied action, security warning, unexpected data transmission, rate limit, or approval boundary. Do not bypass a challenge or rotate identities. Record the blocker and request the specific missing permission only if the task still needs that step. A canceled or approval-blocked run remains outside the site-failure denominator.

After the pilot, review scoring disagreements and repair the protocol before expanding. A routing comparison is preregistered for exactly 12 matched pairs over at least three UTC dates with both execution orders represented. These are design minimums, not a promise of sufficient statistical power. No repeating schedule has been created.

Inspect results freely for safety and scoring defects, but do not repeatedly check significance and stop at the first favorable result. The supplied confirmatory rule evaluates exactly 12 matched pairs at one final analysis. Additional or adaptive samples remain exploratory unless a revised design was registered before those observations.

# Correctness and fidelity

A pass requires every required task check to pass. HTTP 200, a page title, a player thumbnail, a login shell, or a large extraction alone is not completion. Partial means some requested content or action was obtained but the full task failed. Fail means the attempted task did not satisfy its requirements. Blocked, unsupported, and not run are execution states with an unassessed task result.

For text, check the exact target identity, requested facts, source links, visible section coverage, reading order where relevant, and absence of invented content. For a long transcript, verify opening, middle coverage, and closing anchors. Record expected content units, correct units, omissions, and incorrect additions when a frozen reference permits measurement. A high recall score with invented text must not pass.

For downloads, retain actual readable bytes, sniffed format or MIME evidence, byte count, SHA-256, and content validation. A download link alone fails the task. For video, require at least five seconds of advancing playback time and two visibly changing frames. A static poster is insufficient. Audio remains unknown unless actually observed; do not infer it from frames.

Freeze ground truth from the official page, known fixture, or an independently reviewed visible reference. Do not automatically treat either tool’s extraction as the answer key. An adjudicator should score outputs without seeing the browser label where feasible. Store scorer identity and adjudication time. If truth remains ambiguous, use an unscorable reference and exclude the pair rather than award a pass.

The persistence case saves the returned job or tab identity, pauses polling for 30 seconds, and retrieves that same object. This establishes continuity across a no-poll interval only. A client restart, true disconnection, browser restart, and server restart are different experiments. Never claim one was tested by another, and do not restart a live service for this eval.

# Outcome classification

Classify the observed boundary as DNS, TLS, connector transport, page access, bot challenge, render, extraction, interaction, download, authentication, handoff, unknown, or none. Preserve the literal observable error in redacted evidence. Do not infer DNS, firewall rules, HTTP headers, IP reputation, or a server root cause from a generic tool error.

A connector transport failure means the tool could not dispatch or retrieve work. A page-access failure means the browser made an attempt but did not reach the intended content. A render failure means the required UI did not become available. Extraction failure means the content was accessible but the requested representation was missing or wrong. Interaction and download failures concern the specified action or artifact. Authentication and handoff remain separate user-effort boundaries.

Availability is a separate scorecard: scheduled opportunities, successful connector dispatch, usable browser controls, control-site results, time unavailable, and recovery. Keep unplanned outages in that scorecard. A current routing fallback may use an available product, but the outage supplies no evidence that it is better on the target website.

Do not fabricate observations for blocked cases. The delivered observations log is empty. The scheduled rows are not run. The separate availability record captures the one current Patronus transport check, and fixture-discovery results are explicitly labeled web textual fetch.

# Evidence and privacy

Each executed arm needs canonical and final URL, UTC start and end, manifest hash, version and session metadata, job or tab identifier, check-level scores, literal error if any, and references to supporting evidence. For visual claims, record a before and after screenshot or equivalent visual evidence with time and hash. For text and files, retain bounded output and byte-validation evidence.

Screenshots are private evaluation evidence unless explicitly requested as deliverables. Do not upload browser screenshots to Library merely to package this kit. Never include screenshots with personal or payment information in user-facing outputs. Redact query tokens, private identifiers, cookies, authorization headers, credentials, and order details. Store only evidence needed to audit the score. Use a protected evidence location and the user’s retention preferences.

For gated cases, reference the approval without copying secrets. Government legal agreement acceptance and highly sensitive data entry remain user-only. The eval cannot authorize them. Authentication setup and CAPTCHA work need their applicable permission. Public representative fixtures run first; the gated cases remain pending until exact targets, equivalent prerequisites, and authority are established.

# Metrics and routing decisions

Report per-case completion rates, partial results, failure-stage distribution, first-attempt reliability, final reliability after the permitted retry, and temporal stability. Include end-to-end task latency, first useful content latency when observable, tool calls including polling, user intervention count, and active user time. Timeout values are censored observations; retain their budgets and report them with failures instead of hiding them in successful-only latency.

Report median latency with sample count. Publish p95 only with at least 20 successful observations, and flag that this still gives an unstable tail estimate. Compare speed on the subset where both arms completed the same task; also show completion and timeout rates so a fast failure cannot look efficient. Latency is not a causal browser-engine measurement when profiles or network conditions differ.

Cost is null unless an actual charge or metering source is visible. Do not turn tool calls into invented dollar estimates. Costs can be combined only with the same currency, comparable included charges, and complete observation coverage. Show cost coverage and missingness.

The analyzer uses matched pairs, the absolute completion-rate difference, and an exact two-sided McNemar test on discordant pairs. It applies a conservative Bonferroni adjustment across resolved primary cases or the number of observed strata, whichever is larger. Descriptive Wilson intervals are included for each arm; repeated trials of one site are not independent generalization across the web.

A completion-based first-route recommendation is assessed once at the fixed endpoint of 12 matched pairs on at least three dates, counterbalanced order, a gain of at least 20 percentage points, and adjusted p at or below 0.05. Otherwise say insufficient evidence or no clear winner. If both always pass, do not invent an accuracy winner; use paired latency, user effort, and observed costs as a separate practical tie-break discussion. These thresholds are a predeclared decision policy, not a guarantee of scientific certainty.

Keep the recommendation keyed to case, domain context, mode, profile, and versions. Do not generalize a public X result to all social sites, or an authenticated government result to public pages. Add unsupported capability and current availability notes beside the measured routing result. Recheck after a meaningful product or site change rather than reuse an obsolete rule.

The validator rejects duplicated planned slots or reused observation provenance, mismatched reference hashes, unverified execution mode, out-of-budget passes, invalid numeric values, and transport failures labeled as site trials. The analyzer derives execution order from actual UTC timestamps, excludes overlapping arms and ambiguous failure attribution, and reports mode-specific operational availability beside conditional task results.

# Using and integrating the kit

The Python harness has no third-party dependencies and performs no network requests. Use it to generate schedules, validate manually or adapter-recorded JSONL observations, and generate per-case analysis. Synthetic unit-test fixtures are kept inside the tests and are never included as measured observations.

The README lists the exact commands. The pilot schedule is already generated. Do not overwrite the empty observation log with a schedule and present it as results. Copy each assigned row into observations only when recording its actual state, evidence, or execution.

After Alpha access returns, first read the repository instructions and live Patronus capabilities. Place the kit in a reviewable evaluation directory, implement only the adapters supported by those live interfaces, and run the public pilot. Validate outputs before making claims. Integration, commit, push, deployment, authentication changes, and recurring jobs are not performed by this artifact. Follow the user’s applicable approval rules before any of those actions.
